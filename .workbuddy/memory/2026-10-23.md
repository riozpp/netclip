## 小红书解析彻底修复（视频笔记验证通过）

### 根因链（三个 bug 叠在一起）

1. **短链展开泄漏连接**：`expandXhsShortLink` / `expandShortLink` 拿到 302 的 `location` 后直接 return，响应体既不读也不 cancel。
   - 症状极具迷惑性：通道本身 500ms 就出结果，但整个请求要 8–17s 才返回。
   - 修法：新增 `releaseBody(res)`（在 `src/lib/http.js`），所有「只读响应头」的路径都调用它。

2. **unhandled rejection 直接杀 worker（这是 502 的真凶）**：
   - `Promise.race([work, guard])` 超时先返回后，落败的 `work` 稍后 reject，没人 await 它 → Workers 视为 unhandled rejection → **整个请求返回 502**（不是 500，`catch` 根本收不到）。
   - 同样的问题存在于 `withTimeout`：guard 先 reject 后，原 promise 再 reject 就成了孤儿。
   - 修法：在 race 之前先给原 promise 挂空 catch（`work.catch(() => {})` / `promise.catch(() => {})`）。
   - **排错启示**：`502 + Retry-After` 且 `catch` 抓不到任何异常时，优先查 unhandled rejection。

3. **出口被封**：Cloudflare 边缘 IP 访问 `xiaohongshu.com` 一律 302 到 `/website-login/captcha`（IP 级人机墙）。Google 翻译中转全部 429，jina/codetabs/allorigins/corslol 也都不可用。

### 最终方案：走 rednote 国际站

- `www.rednote.com/discovery/item/<id>?xsec_token=…` + **Bytespider 蜘蛛 UA** → 200，1428ms，完整 SSR。
- 同一 `noteId` 在国内站与国际站通用，数据结构一致（`noteData.data.noteData`）。
- **反直觉**：中国大陆本机访问 rednote 返回 `error_code 300031`（地区限制），这个域名恰好在境外出口可用。所以它的可用性只能在 Cloudflare 上验证，本地测会误判。

### 媒体域名

- rednote 返回的图片/视频走 `rednotecdn.com`，国内站是 `xhscdn.com`。**两者都要进 `src/proxy.js` 的 `ALLOWED_HOSTS`**，否则下载/封面 403。
- 视频 `masterUrl` 的 http 与 https 版本实测都是 206，中国大陆直连可下载（45MB h264 / 208s）。

### 稳定性

- 压测 6/6 成功，1.07–5.33s（平均 ~2.9s）。
- 降级链：`rednote` → `rednote explore 路径` → 国内站直连 → Google 翻译中转（3500ms/个）→ `XHS_PROXY` → 无 token 兜底。
- `cacheWrite` 改成不 await（fire-and-forget），写缓存失败不该拖慢响应。

### 排错工具经验

- `wrangler tail` 走本地代理会 502，全程不可用。改用两种手段：
  1. 临时 `/api/diag/xhs?url=&ch=` 诊断端点（可指定单通道、返回 status/location/len/stateKeys）；
  2. 本地 `wrangler dev --local` 复现，能直接看到完整 JSON 结果。
- 诊断端点上线前必须删除（本次已删，`grep diagnoseXhs` 为 0）。
- 用 curl 测 CDN 可用性时务必加 `--noproxy '*'`：走代理会拿到假 404（代理出口节点没有该 key）。
- Git Bash 里 `$p` 拼接的 `/` 会被 MSYS 转成 Windows 路径，测 URL 时要 `export MSYS_NO_PATHCONV=1`。

## 追加：25–60s「挂死」的真正原因（重要）

修完上面三个 bug 后仍有一部分请求挂到 25s/60s 才结束，逐一排除后定位到**平台行为**：

**Cloudflare Workers 会等所有 pending subrequest 结束才发响应。**
即使代码已经 `return new Response(...)`，只要还有一个 `fetch` 挂着没结束，worker 就不会把响应发给客户端。

决定性实验（临时端点 `/api/_sig?w=timer4`）：
- 后台挂一个 `fetch(rednote, AbortSignal.timeout(25000))`
- 主流程 `await` 一个 3000ms 定时器
- 结果：**定时器 ms=3000 准时抛错（说明 setTimeout 完全正常）**，但 **curl 总耗时 34s**

即：超时逻辑一直是有效的，问题在「被放弃的 fetch 还在后台挂着，拖住了响应发送」。

### 因此的修法
1. `request()` 从 `AbortSignal.timeout()` 改成 `AbortController` + 超时后**手动 `controller.abort()`** —— 光是 `Promise.race` 提前返回没用，必须真的断连接。
2. `res.text()` 换成 `readTextSafe()`（分块 `reader.read()`，每块重新计时 + `reader.cancel()`）。实测 `https://www.rednote.com/` 的 body 会「拿到响应头后永久卡住」，且此时事件循环被占住，连 `setTimeout` 都不再触发（整条请求 60s 无响应就是这么来的）。
3. KV 读写全部封顶（`kv.get` 实测有一次卡 20s）；`caches.default.put` 也要封顶。
4. **并发会让整体更不稳定**：3 个通道并行时挂死率反而更高，改回串行。
5. 移除必然失败的通道：`xiaohongshu.com` 直连（CF 出口 100% 302 到 `/website-login/captcha`）、Google 翻译中继（长期 429）。

### 仍未 100% 消除
`controller.abort()` 在部分挂起场景下无法立刻终止 CF 底层的 subrequest，因此仍会偶发（约 1/4）到 25s。前端因此加了 **14s 超时 + 自动重试一次**，第二次基本都命中 KV 缓存（1.0–1.6s）。

### 缓存注意
`caches.default` 只在当前边缘节点有效；已绑定 KV `CACHE_KV`（id `3e9b8c0f5b8e4747ae1bfdb39c64c01f`）做跨节点共享。
**KV 列表 API 有同步延迟**：刚写入的 key 在 `keys?limit=` 里查不到，但 `get` 能读到，别因此误判「没写入」。

### 环境限制
